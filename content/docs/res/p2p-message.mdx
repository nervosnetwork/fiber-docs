Fiber 0.10.x introduces V2 channel messaging. New channels require both peers to support V2. Existing V1 channels keep their legacy messages and remain usable in 0.10.1; upstream plans to remove V1 support in the next major release.

The definitions below come from the [0.10.1 Molecule schema](https://github.com/nervosnetwork/fiber/blob/v0.10.1/crates/fiber-types/src/schema/fiber.mol). This schema is the wire-format source of truth. Fiber is inspired by [BOLT 02](https://github.com/lightning/bolts/blob/master/02-peer-protocol.md), but its Molecule messages are not Lightning wire messages.

## V2 Capability and Channel Features

`Init.features` advertises `CHANNEL_V2` through feature bits 6/7. The official 0.10.1 node advertises `CHANNEL_V2_OPTIONAL`. The persisted channel feature byte is `0x1` for V2 and `0x0` for Legacy V1.

V2 separates commitment-owner, revocation, and closing nonce sessions. It uses full 32-byte payment hashes in settlement witnesses and 58-byte commitment-lock args, including the feature byte. Legacy channels retain 20-byte on-chain payment-hash prefixes and 57-byte args. The configured commitment contract must support the V2 layout before a node advertises this capability.

## Establishing a V2 Channel

The initiator sends `OpenChannelV2`; the acceptor replies with `AcceptChannelV2`. The peers collaborate on the funding transaction with `TxUpdate` and `TxCompleteV2`, exchange initial commitment signatures and funding `TxSignatures`, and wait for on-chain confirmation before exchanging `ChannelReadyV2`.

For CKB channels, wire `funding_amount` is the spendable amount after the local reserve is deducted from the RPC contribution. `reserved_ckb_amount` carries that reserve separately. For UDT channels, `funding_amount` is the raw token amount and CKB reserve is additional.

## V2 Message Definitions

`Pubkey` is 33 bytes, `PubNonce` is 66 bytes, and `PubNonceOpt` is an optional public nonce. `Script`, `ScriptOpt`, `Transaction`, integer types, and byte vectors are defined by the imported CKB/Fiber Molecule schemas.

```text
table OpenChannelV2 {
    chain_hash: Byte32,
    channel_id: Byte32,
    funding_udt_type_script: ScriptOpt,
    funding_amount: Uint128,
    shutdown_script: Script,
    reserved_ckb_amount: Uint64,
    funding_fee_rate: Uint64,
    commitment_fee_rate: Uint64,
    max_tlc_value_in_flight: Uint128,
    max_tlc_number_in_flight: Uint64,
    commitment_delay_epoch: Uint64,
    funding_pubkey: Pubkey,
    tlc_basepoint: Pubkey,
    first_per_commitment_point: Pubkey,
    second_per_commitment_point: Pubkey,
    channel_announcement_nonce: PubNonceOpt,
    initial_commitment_nonce: PubNonce,
    channel_flags: byte,
    channel_features: byte,
}

table AcceptChannelV2 {
    channel_id: Byte32,
    funding_amount: Uint128,
    shutdown_script: Script,
    reserved_ckb_amount: Uint64,
    max_tlc_value_in_flight: Uint128,
    max_tlc_number_in_flight: Uint64,
    funding_pubkey: Pubkey,
    tlc_basepoint: Pubkey,
    first_per_commitment_point: Pubkey,
    second_per_commitment_point: Pubkey,
    channel_announcement_nonce: PubNonceOpt,
    initial_commitment_nonce: PubNonce,
    channel_features: byte,
}

table CommitmentSignedV2 {
    channel_id: Byte32,
    commitment_number: Uint64,
    funding_tx_partial_signature: Byte32,
    funding_nonce: PubNonce,
    revocation_nonce: PubNonceOpt,
}

struct RevokeAndAckV2 {
    channel_id: Byte32,
    commitment_number: Uint64,
    revocation_partial_signature: Byte32,
    revocation_nonce: PubNonce,
    next_per_commitment_point: Pubkey,
    next_commitment_nonce: PubNonce,
}

struct ChannelReadyV2 {
    channel_id: Byte32,
    next_commitment_number: Uint64,
    next_commitment_nonce: PubNonce,
}

struct ReestablishChannelV2 {
    channel_id: Byte32,
    next_commitment_number: Uint64,
    next_ack_number: Uint64,
    next_local_commitment_nonce: PubNonce,
}

table ShutdownV2 {
    channel_id: Byte32,
    fee_rate: Uint64,
    close_script: Script,
    closing_nonce: PubNonce,
}

struct ClosingSignedV2 {
    channel_id: Byte32,
    partial_signature: Byte32,
}

struct TxCompleteV2 {
    channel_id: Byte32,
    initial_commitment_nonce: PubNonce,
}
```

## Shared Transport, Funding, and TLC Messages

V2 retains the shared `Init`, transaction collaboration, TLC add/remove, and forwarding-policy messages below. A channel's negotiated version determines which commitment, acknowledgement, readiness, reestablishment, and close variants surround them.

```text
table Init {
    features: Bytes,
    chain_hash: Byte32,
}

table TxUpdate {
    channel_id: Byte32,
    tx:         Transaction,
}

table TxSignatures {
    channel_id: Byte32,
    witnesses:  BytesVec,
}

table TxAbort {
    channel_id: Byte32,
    message:    Bytes,
}

table AddTlc {
    channel_id:     Byte32,
    tlc_id:         Uint64,
    amount:         Uint128,
    payment_hash:   Byte32,
    expiry:         Uint64,
    hash_algorithm: byte,
    // This is the packet each hops need to decrypt and determine
    // which nodes to forward (or accept the tlc if it is the final node).
    onion_packet:   Bytes,
}

struct RemoveTlcFulfill {
    payment_preimage:   Byte32,
}

table TlcErrPacket {
    onion_packet:        Bytes,
}

union RemoveTlcReason {
    RemoveTlcFulfill,
    TlcErrPacket,
}

table RemoveTlc {
    channel_id:         Byte32,
    tlc_id:             Uint64,
    reason:             RemoveTlcReason,
}

struct UpdateTlcInfo {
    channel_id: Byte32,
    timestamp: Uint64,
    channel_flags: Uint32,
    tlc_expiry_delta: Uint64,
    tlc_minimum_value: Uint128,
    tlc_fee_proportional_millionths: Uint128,
}
```

## Commitment and Acknowledgement Rules

V2 binds nonce advertisements and partial signatures to numbered commitment sessions. Add/remove updates remain pending until the outgoing commitment save records their TLC IDs, contents, counters, and replay log together. Updates are then sent in order before the corresponding `CommitmentSignedV2`.

On reconnection, `ReestablishChannelV2` exchanges the next commitment and acknowledgement counters with the advertised local nonce. Reconciliation replays the durable log in its original order. A current store can replay its saved signing intent; an older restored V2 backup cannot establish safe nonce use and remains quarantined as `Stale`.

## Closing and Recovery

Cooperative closing exchanges fresh `ShutdownV2` closing nonces and `ClosingSignedV2` partial signatures. Pending TLCs finish acknowledgement and balance application before the close transaction is fixed. The durable closing session retains the exact transaction, signing context, and partial responses so a reconnect can replay the same close safely.

A peer that withholds a required acknowledgement or close response can trigger the bounded watchdog. Duplicate messages and live reconnects do not extend the persisted peer-wait deadline. Force closing uses the latest usable saved commitment transaction and supersedes cooperative publication.

For externally funded openings, signed submission disables ordinary time-based cancellation. See [External Funding](/docs/concept/channels/external-funding) for conflicting-input and force-close recovery.
